## 1. Мета роботи

Дослідити переваги та недоліки PLINQ порівняно зі звичайним LINQ, виміряти швидкість обробки великих колекцій та дослідити проблеми потокобезпечності під час паралельного виконання операцій.

## 2. Виконання роботи

Було створено консольний проєкт IndependentWork12.

Для дослідження використано колекції випадкових цілих чисел трьох розмірів:

- 1 000 000 елементів;
- 5 000 000 елементів;
- 10 000 000 елементів.

Для обробки даних реалізовано метод HeavyCalculation(), який виконує послідовність математичних операцій: обчислення квадратного кореня, синуса, косинуса та модуля числа.

## 3. Порівняння LINQ та PLINQ

Для звичайного LINQ використано:

```csharp
numbers
    .Where(x => x % 3 == 0)
    .Select(HeavyCalculation)
    .ToArray();
```

Для PLINQ використано:

```csharp
numbers
    .AsParallel()
    .Where(x => x % 3 == 0)
    .Select(HeavyCalculation)
    .ToArray();
```

Час виконання вимірювався за допомогою класу Stopwatch.

### Результати експериментів

| Кількість елементів | LINQ (мс) | PLINQ (мс) |
|---|---:|---:|
| 1 000 000 | Заповнити | Заповнити |
| 5 000 000 | Заповнити | Заповнити |
| 10 000 000 | Заповнити | Заповнити |

*Примітка: результати потрібно заповнити після запуску програми на власному комп'ютері.*

## 4. Аналіз продуктивності

PLINQ використовує декілька потоків для одночасної обробки елементів колекції.

Перевагою PLINQ є можливість розподілити обчислення між доступними ядрами процесора. Це особливо корисно для великих колекцій та складних математичних операцій.

Звичайний LINQ виконує обчислення послідовно, тому для великих обсягів складних операцій може потребувати більше часу.

Однак PLINQ не завжди швидший. Його використання потребує додаткових ресурсів для створення потоків, розподілу завдань та об'єднання результатів.

## 5. Дослідження потокобезпечності

Під час експерименту було створено спільний лічильник, який змінювався всередині PLINQ-запиту.

У небезпечному варіанті використовувалася операція:

```csharp
unsafeCounter++;
```

Проблема полягає в тому, що операція збільшення лічильника не є атомарною. Кілька потоків можуть одночасно прочитати та змінити значення змінної.

У результаті частина змін може загубитися, а отримане значення буде меншим за очікуване.

### Виправлення проблеми

Для виправлення використано:

```csharp
Interlocked.Increment(ref safeCounter);
```

Метод Interlocked.Increment забезпечує атомарне збільшення значення змінної.

Після виправлення результат відповідає очікуваній кількості елементів.

## 6. Висновки

Під час виконання самостійної роботи було досліджено технологію PLINQ та порівняно її зі звичайним LINQ.

Було створено колекції різного розміру, реалізовано обчислювально інтенсивну операцію та виміряно час її виконання за допомогою Stopwatch.

Встановлено, що PLINQ може забезпечувати значне прискорення обробки великих обсягів даних, особливо коли кожен елемент потребує складних обчислень.

Також було досліджено проблему потокобезпечності. Використання спільної змінної без синхронізації призводить до можливих помилок. Для усунення проблеми використано Interlocked.Increment.

Отже, PLINQ доцільно використовувати для великих обсягів незалежних обчислень. Проте перед його застосуванням необхідно враховувати витрати на паралелізацію та забезпечувати потокобезпечність спільних ресурсів.

## 7. Контрольні запитання

**1. За яких умов PLINQ зазвичай дає виграш у продуктивності?**

Коли обробляється велика кількість даних, а кожен елемент потребує значних незалежних обчислень. Також важливо, щоб комп'ютер мав декілька доступних ядер процесора.

**2. Чому побічні ефекти всередині PLINQ можуть призводити до некоректних результатів?**

Тому що декілька потоків можуть одночасно змінювати спільні дані. Це створює умови для конфліктів та втрати змін.

**3. Для чого важливо порівнювати кілька розмірів колекції?**

Щоб визначити залежність продуктивності від обсягу даних та встановити, за яких умов паралельна обробка стає ефективнішою.

**4. Які висновки слід зробити, якщо PLINQ виявився повільнішим за LINQ?**

Це означає, що витрати на паралелізацію перевищили вигоду від одночасного виконання операцій. У такому випадку звичайний LINQ може бути ефективнішим.
